## 分层约束

- 后端：路由 → 服务层 → 数据访问，禁止跨层调用
- 前端：页面 → 组件/Hook → 请求服务，状态集中管理
- 所有异步 I/O 必须在各自框架的异步上下文内完成
- 环境相关变量一律通过 .env 注入

## 技术选型理由

### 后端

| 技术 | 选型理由 |
|------|----------|
| **Python 3.13** | 项目面向企业级后台管理，Python 在运维、测试、数据处理的生态成熟；3.13 进一步优化了性能与错误回溯，团队 Python 经验丰富 |
| **FastAPI** | 原生异步支持，与项目"所有 I/O 必须异步"的约束自然契合；基于 Pydantic + Type Hints 自动生成 OpenAPI 文档，降低前后端联调成本；高性能（基于 Starlette），社区活跃 |
| **SQLAlchemy 2.0 async** | Python 生态最成熟的 ORM，2.0 版本统一了同步/异步 API 风格；自带连接池、迁移工具（Alembic）支持，且能屏蔽 MySQL/PostgreSQL 方言差异 |
| **asyncmy / asyncpg** | 分别为 MySQL 和 PostgreSQL 提供异步驱动，与 SQLAlchemy 2.0 async 原生集成，满足"双后端兼容"的约束 |
| **Redis (redis.asyncio)** | 满足三大核心需求：权限缓存（减少 DB 查询）、系统配置缓存（热加载）、操作日志异步队列；官方 asyncio 客户端保证异步兼容 |
| **passlib + python-jose** | passlib 是密码哈希的事实标准（支持 bcrypt/argon2），python-jose 提供 JWT 签发与验证，两者组合是 FastAPI 生态中认证的常见方案 |
| **uv** | 比 pip/poetry 更快的 Python 包管理器，基于 Rust 实现，契合项目对开发效率的追求 |
| **pytest-asyncio + httpx** | pytest-asyncio 提供异步测试支持；httpx.AsyncClient 可直接与 FastAPI TestClient 配合，无需启动真实服务器即可测试 |
| **ruff + mypy** | ruff 是 Rust 实现的极速 Python linter，替代 flake8/isort；mypy 提供静态类型检查，与"所有函数必须有类型注解"的规范配合 |

### 前端

| 技术 | 选型理由 |
|------|----------|
| **React 18+** | 生态最成熟的前端框架，社区资源丰富；Concurrent Mode 与 Suspense 为未来性能优化留出空间；函数式组件 + Hooks 模式简洁可测试 |
| **TypeScript** | 静态类型系统大幅减少运行时类型错误，与后端 Pydantic 模型形成"双端类型安全"；对 API 响应、组件 props 提供编译时校验 |
| **Vite** | 基于 ESBuild 的开发服务器实现秒级 HMR（热更新），远超 Webpack 的冷启动速度；生产构建基于 Rollup，输出优化良好 |
| **Ant Design 5.x** | 专为中后台场景设计的 UI 框架，内置 Table、Form、Tree、TreeSelect 等 60+ 组件，覆盖本项目所有管理页面的 UI 需求；5.x 使用 CSS-in-JS（cssinjs），无需额外配置 Less/Sass |
| **Zustand** | 比 Redux 更轻量的状态管理库，API 简洁（无需 action/reducer 样板代码），TypeScript 支持优秀；适合本项目"全局用户信息 + 权限状态"的有限状态场景 |
| **React Router v6** | 嵌套路由与布局路由原生支持，适合本项目的 MainLayout 嵌套子页面结构；`loader`/`action` 数据加载模式可与动态路由结合 |
| **axios** | 拦截器机制（请求注入 token、响应自动刷新）完美匹配 JWT 认证流；请求/响应拦截器可集中处理错误、token 自动刷新等横切关注点 |
| **pnpm** | 相比 npm/yarn，pnpm 通过硬链接节省磁盘空间，安装速度更快，monorepo 场景支持更好 |
| **Vitest + React Testing Library** | Vitest 与 Vite 共享配置，无需额外转译，运行速度远快于 Jest；RTL 倡导"按用户行为测试"而非测试实现细节 |

### 其他基础设施

| 技术 | 选型理由 |
|------|----------|
| **MySQL / PostgreSQL** | 双后端支持：MySQL 是多数国内企业的标配，PostgreSQL 则提供更丰富的扩展（如 JSONB、全文检索），两者通过 SQLAlchemy 通用类型屏蔽差异 |
| **Ant Design Icons** | 与 Ant Design 原生集成，图标资源丰富，满足菜单管理模块的图标选择器需求 |
| **dayjs** | 轻量级日期库（2KB），API 兼容 Moment.js，适合前端日期格式化与日志时间范围选择器 |
| **Alembic** | SQLAlchemy 官方迁移工具，异步模板支持 async engine，保证 schema 变更可追溯、可回滚 |

**关键约束**：
- 密码永不返回前端，仅用于服务端校验
- access token 过期后，axios 拦截器自动用 refresh token 换取新 token
- 刷新失败（refresh token 也过期）→ 清除 Zustand store → 跳转登录页
- 超级管理员跳过所有权限校验，直接放行

```
┌──────────┐    ┌────────────┐    ┌────────────┐    ┌──────────┐
│ 业务 Service │    │ Redis 列表   │    │ 后台 Worker  │    │ DB       │

│            │    │ 日志 JSON   │    │            │    │          │
│            │    │            │    │            │    │          │
│            │    │            │───►│ ③ BRPOP    │    │          │
│            │    │            │    │ 攒够 N 条   │    │          │
│            │    │            │    │ 或每 5 秒   │───►│ ④ BULK   │
│            │    │            │    │            │    │ INSERT   │
│            │    │            │    │            │    │          │
│            │    │            │    │ ⑤ 写入成功  │◄───┤          │
```

**关键约束**：
- 业务接口仅执行 LPUSH 操作（O(1) 复杂度），不阻塞主流程
- Worker 在应用启动时创建为 asyncio 后台任务，与应用生命周期绑定
- 日志队列积压时自动降级（限制队列最大长度，超限则丢弃旧日志）
- 日志记录不可影响主业务事务的成功与否

## 接口设计原则

### 1. RESTful 版本化

- 所有 API 以 `/api/v1/` 为前缀，后续版本升级时改为 `/api/v2/`
- 示例：`POST /api/v1/users`、`GET /api/v1/departments/tree`
- 版本通过路由前缀实现，后端目录结构对应：`app/api/v1/`

### 2. 统一响应格式

```json
// 成功响应
{
  "code": 0,
  "data": { ... },
  "message": "ok"
}

// 分页响应
{
  "code": 0,
  "data": {
    "items": [ ... ],
    "total": 100,
    "page": 1,
    "page_size": 10
  },
  "message": "ok"
}

// 错误响应
{
  "code": 40001,
  "data": null,
  "message": "用户名已存在"
}
```

- `code`：0 表示成功，非 0 表示业务错误码（如 40001 参数错误、40002 资源冲突、40101 Token 过期）
- `data`：实际数据负载，失败时为 `null`
- `message`：成功时为 `"ok"`，失败时为可读错误描述

### 3. HTTP 状态码使用规范

| 状态码 | 场景 |
|--------|------|
| 200 | 查询/更新/删除成功 |
| 201 | 创建成功 |
| 400 | 参数校验失败（Pydantic 校验错误） |
| 401 | 未认证或 Token 过期/无效 |
| 403 | 已认证但无权限（权限标识不足） |
| 404 | 资源不存在 |
| 409 | 业务冲突（如用户名重复、删除被引用的资源） |
| 422 | 请求体格式错误（Pydantic 校验失败） |
| 500 | 服务器内部错误 |

### 4. CRUD 接口命名规范

| 操作 | HTTP 方法 | URL 示例 | 权限标识示例 |
|------|-----------|----------|-------------|
| 列表分页 | `GET` | `/api/v1/users?page=1&page_size=10` | `system:user:list` |
| 查询详情 | `GET` | `/api/v1/users/{id}` | `system:user:query` |
| 新增 | `POST` | `/api/v1/users` | `system:user:create` |
| 编辑 | `PUT` | `/api/v1/users/{id}` | `system:user:update` |
| 删除 | `DELETE` | `/api/v1/users/{id}` | `system:user:delete` |

### 5. 接口请求/响应规范

- **请求体**：一律使用 JSON（`application/json`），文件上传除外
- **分页参数**：统一为 `page`（从 1 开始）和 `page_size`（默认 10，最大 100）
- **排序参数**：统一为 `sort_by`（字段名）和 `sort_order`（`asc`/`desc`）
- **筛选参数**：使用 Query 参数（如 `?username=xxx&status=1`）
- **日期格式**：请求使用 ISO 8601（`2025-01-01T00:00:00Z`），响应使用时间戳或 ISO 8601

### 6. 特殊接口设计

| 接口 | 说明 |
|------|------|
| `GET /.../tree` | 返回树形结构数据（部门树、权限树、菜单树） |
| `PUT /{id}/status` | 启用/禁用状态切换 |
| `POST /{id}/reset-password` | 密码重置（返回无敏感信息） |
| `PUT /{id}/roles` | 角色分配 |
| `PUT /{id}/permissions` | 权限分配 |
| `GET /menus/user-menus` | 当前用户可访问菜单（动态路由用） |
| `POST /system-configs/refresh-cache` | 手动刷新配置缓存 |
