# 产品设计文档 (PDD)

> 本文档基于 "基础后台管理系统" 的定位，围绕用户管理、部门管理、角色管理、权限管理、菜单管理、系统配置、操作日志七大核心模块进行需求定义。

---

## 1. 摘要

本文档定义了一套通用的基础后台管理系统（Admin Dashboard）的产品需求。系统采用前后端分离架构（FastAPI + React），聚焦于企业内部管理场景中最核心的七大模块：**用户管理**、**部门管理**、**角色管理**、**权限管理**、**菜单管理**、**系统配置**、**操作日志**。目标是为上层业务系统提供开箱即用的组织架构与权限基础设施，支持基于 RBAC（Role-Based Access Control）模型的细粒度权限控制，包含页面级和按钮级的权限管控，并提供统一的系统参数配置与操作审计能力。

---

## 2. 目标

- **用户管理**：提供用户的增删改查、状态管理（启用/禁用）、密码重置、所属部门与角色分配功能。
- **部门管理**：提供多级树形部门结构的增删改查，支持部门与用户的关联管理。
- **角色管理**：提供角色的增删改查，支持角色与权限的绑定、角色与用户的关联。
- **权限管理**：提供粒度可配置的权限资源定义（菜单权限、按钮权限、API 权限），支持树形层级展示。
- **菜单管理**：提供动态菜单树的配置维护，支持前端动态路由生成，页面隐藏、排序、图标等元信息管理。
- **权限体系完整闭环**：实现 "用户 → 角色 → 权限 → 菜单" 的完整链路，确保前端路由守卫、按钮级显隐与后端 API 访问控制一致。
- **系统配置**：提供全局系统参数的统一管理，支持多类型配置项（文本、数值、布尔、选择等），按分组（如基本设置、安全设置）归类维护，支持配置项缓存刷新。
- **操作日志**：自动记录用户的关键操作行为（谁、何时、做了什么、操作了哪个模块），提供多维度的日志检索与详情查看，支持定期清理策略，满足基本审计合规要求。

---

## 3. 非目标

- 不包含移动端适配（仅针对桌面端浏览器）。
- 不包含 WebSocket 实时推送消息（如在线人数、站内信）。
- 不包含单点登录（SSO）、OAuth 2.0 第三方登录等企业级认证集成（但 JWT 认证体系会预留扩展点）。
- 不包含审批工作流引擎、数据大屏、国际化（i18n）等特性。
- 不提供多租户（SaaS Multi-Tenant）能力，系统定位为单组织内部管理后台。
- 操作日志仅限于记录用户对系统资源（用户、部门、角色、权限、菜单、系统配置）的管理操作，不包含业务数据变更的完整审计追踪（如某条订单的字段级变更历史）。

## 4. 功能需求

### 4.1 用户管理

| 功能 | 描述 |
|------|------|
| 用户列表 | 分页展示用户信息，支持按用户名、邮箱、手机号、部门、角色、状态筛选 |
| 新增用户 | 录入用户名、邮箱、手机号、密码（默认密码规则）、所属部门、角色 |
| 编辑用户 | 修改用户的基本信息（用户名不可修改或带约束） |
| 删除用户 | 逻辑删除或物理删除（需确认设计），需校验用户是否有关联业务数据 |
| 状态管理 | 启用/禁用用户账号，禁用后无法登录系统 |
| 密码重置 | 将用户密码重置为预设默认密码 |
| 角色分配 | 支持为用户分配一个或多个角色 |
| 部门分配 | 支持为用户分配一个或多个部门（主部门 + 副部门） |
| 个人信息 | 当前登录用户可查看/编辑自己的基础信息 |

### 4.2 部门管理

| 功能 | 描述 |
|------|------|
| 部门树 | 以树形结构展示所有部门，支持展开/折叠 |
| 新增部门 | 指定部门名称、上级部门、排序号、负责人、状态 |
| 编辑部门 | 修改部门信息 |
| 删除部门 | 需校验：有子部门时禁止删除，有用户关联时禁止删除 |
| 部门用户 | 查看部门下的用户列表，支持在部门详情页快捷管理成员 |
| 排序 | 同级部门支持拖拽或手动输入排序号调整顺序 |

### 4.3 角色管理

| 功能 | 描述 |
|------|------|
| 角色列表 | 分页展示角色，支持按角色名、状态筛选 |
| 新增角色 | 录入角色名称、角色编码（唯一标识，如 `admin`）、角色描述 |
| 编辑角色 | 修改角色信息（角色编码不可修改） |
| 删除角色 | 需校验：有关联用户时禁止删除 |
| 权限分配 | 为角色分配菜单权限、按钮权限、API 权限（见 4.4） |
| 角色成员 | 查看并管理该角色下的用户列表 |

### 4.4 权限管理

| 功能 | 描述 |
|------|------|
| 权限列表 | 以树形结构展示所有权限资源，区分权限类型 |
| 权限类型 | 支持三种粒度的权限：**菜单权限**（页面访问）、**按钮权限**（页面内操作）、**API 权限**（后端接口） |
| 新增权限 | 录入权限名称、权限编码（如 `system:user:create`）、权限类型、上级权限、API 路径与请求方法 |
| 编辑/删除权限 | 需校验：有角色引用时禁止删除，给出提示 |
| 权限标识规范 | 采用冒号分隔的命名规范：`模块:子模块:操作`，如 `system:user:list`、`system:role:create` |

### 4.5 菜单管理

| 功能 | 描述 |
|------|------|
| 菜单树 | 以树形结构展示所有菜单项，支持展开/折叠 |
| 新增菜单 | 录入菜单名称、图标、路由路径、前端组件路径、上级菜单、排序号、是否隐藏（用于作为纯目录） |
| 编辑/删除菜单 | 修改菜单元信息；删除时需校验是否有子菜单 |
| 关联权限 | 每个菜单可绑定一个或多个权限标识，用于路由守卫判断 |
| 动态路由 | 前端根据当前用户权限动态生成可访问的路由表 |
| 外链支持 | 菜单类型支持"内部路由"和"外部链接"两种模式 |

### 4.6 系统配置

| 功能 | 描述 |
|------|------|
| 配置分组 | 按分组管理配置项（如"基本设置"、"安全设置"、"邮件设置"、"日志设置"），支持分组的新增、编辑、删除 |
| 配置项管理 | 每个分组下包含若干配置项：配置键（唯一标识）、配置名称、配置值、值类型（字符串/整数/布尔值/JSON/枚举选择）、备注 |
| 配置列表 | 以分组-配置项的两级结构展示，支持按分组筛选、按配置键搜索 |
| 编辑配置 | 根据配置项的值类型动态渲染对应的表单控件（Switch 开关、InputNumber 数字输入、Select 下拉选择等） |
| 生效机制 | 配置修改保存后立即生效（写入数据库并刷新 Redis 缓存），无需重启服务 |
| 缓存刷新 | 支持手动刷新全部配置缓存，用于缓存与数据库不一致时的恢复手段 |
| 访问控制 | 敏感配置项（如邮件密码、密钥）仅超级管理员可见可编辑，普通管理员仅允许查看非敏感配置 |

### 4.7 操作日志

| 功能 | 描述 |
|------|------|
| 日志列表 | 分页展示操作日志，支持按操作用户、操作模块（用户/部门/角色/权限/菜单/系统配置）、操作类型（新增/修改/删除/登录/其他）、操作时间范围筛选 |
| 日志详情 | 查看单条日志的完整信息：操作人、操作人 IP、操作模块、操作类型、操作描述、操作时间、请求参数、请求结果（成功/失败） |
| 操作人追溯 | 点击操作人可跳转至对应用户详情 |
| 日志自动清理 | 支持配置日志保留天数（默认 90 天），超期日志由定时任务自动清理或归档 |
| 操作记录范围 | 自动记录对系统资源（用户/部门/角色/权限/菜单/系统配置）的所有增删改操作，以及用户的登录行为 |
| 日志不可篡改 | 操作日志仅允许查询，不允许修改或删除（除自动清理外），确保审计记录的完整性 |

## 5. 技术约束

- **后端**：Python 3.13 + FastAPI，所有 I/O 操作必须使用异步方式（SQLAlchemy 2.0 async + asyncmy/asyncpg + redis.asyncio）。
- **前端**：React 18 + TypeScript + Vite + Ant Design 5.x，函数式组件 + Hooks，禁用 class 组件。
- **数据库**：MySQL / PostgreSQL 双后端兼容，仅使用 ANSI SQL 与 SQLAlchemy 通用类型，禁止方言特性。
- **认证**：JWT 令牌（access token + refresh token），密码使用 passlib 哈希存储。
- **权限模型**：RBAC（Role-Based Access Control），权限缓存至 Redis 以降低数据库查询频率。
- **状态管理**：前端使用 Zustand 管理全局用户信息和权限状态。
- **API 通信**：前端 axios 统一拦截器处理令牌注入、自动刷新、错误拦截；后端返回统一 JSON 格式 `{"code": 0, "data": ..., "message": "..."}`。
- **数据库迁移**：所有 schema 变更必须生成 Alembic 迁移脚本。
- **环境配置**：所有密钥及连接串通过 `.env` 文件或环境变量注入，禁止硬编码。
- **代码检查**：通过 ruff + mypy（后端）与 ESLint + Prettier（前端）检查。

## 6. 边缘情况

1. **循环引用**：部门树 / 菜单树的上级节点不能指向自身或子节点形成循环，后端需做环检测。
2. **级联删除保护**：
   - 删除部门：如有子部门或关联用户，禁止删除，返回明确错误信息。
   - 删除角色：如有用户关联，禁止删除。
   - 删除权限 / 菜单：如有子节点或已被角色引用，禁止删除。
3. **用户数据完整性**：删除用户前需判断是否存在业务关联数据（如创建的单据），建议采用逻辑删除（`is_deleted` 标记）而非物理删除。
4. **并发冲突**：多个管理员同时修改同一角色权限时，后者应覆盖前者（最终写入覆盖）或使用乐观锁（版本号字段）。
5. **超级管理员保护**：系统预设的超级管理员（如 `admin`）不可被删除、不可被禁用，其角色不可被修改。
6. **权限缓存一致性问题**：角色权限变更后，需主动失效 Redis 中相关用户的权限缓存，确保下次请求生效。
7. **空状态**：所有列表页无数据时，应显示空状态占位图（Ant Design `Empty` 组件），而非空白页面。
8. **异常输入**：树形结构排序号为非数字、唯一字段（用户名/邮箱/角色编码）重复等场景，需后端校验并返回明确错误信息。
9. **数据批量操作**：部门/角色关联大量用户时（如 1000+ 用户），前端展示需采用虚拟滚动或分页，避免 DOM 性能问题。
10. **菜单与权限分离**：菜单树上的菜单项与权限树上的权限项是一对多关系。一个菜单可对应多个按钮权限，但菜单自身的访问权限也需对应一条权限记录。
11. **系统配置缓存穿透**：系统启动时若 Redis 不可用，配置读取应回退到数据库查询，避免因缓存故障导致系统不可用。配置写入时采用"先写数据库，再删除缓存"的策略确保最终一致性。
12. **敏感配置脱敏**：敏感配置项（如 SMTP 密码、密钥）在 API 响应中必须脱敏展示（如 `******`），仅在编辑提交时允许写入新值。前后端均可看到明文的敏感字段不做传输。
13. **操作日志数据量膨胀**：操作日志是典型的高写入、低频查询数据，日均可能产生数千条记录。需提前考虑索引优化（对 user_id、module、action、created_at 建联合索引）和分表/分区策略。
14. **操作日志的异步写入**：业务接口中记录日志不应影响主业务流程。日志写入应采用异步方式（如丢入内存队列后批量写入，或写入独立日志表），避免成为接口性能瓶颈。
15. **并发登录日志**：同一用户短时间内多次登录失败，应记录每次失败的登录尝试，但需避免日志表被恶意频繁登录写爆（可结合 IP 频率限制）。

## 7. 测试计划

### 7.1 后端测试（pytest-asyncio + httpx.AsyncClient）

| 测试范围 | 内容 |
|----------|------|
| 单元测试 | 每个 service 层方法的正常流程与异常流程（如创建用户时用户名重复、删除部门时有子部门、配置值类型校验失败、日志查询参数越界） |
| API 集成测试 | 每个 CRUD 接口的正向流程（200）、认证失败（401/403）、参数校验错误（422）、业务校验失败（409） |
| 权限测试 | 不同角色用户请求受限接口是否返回 403；超级管理员是否拥有全部权限；敏感配置项的非管理员访问是否被拒绝 |
| 树形结构测试 | 部门/菜单树的新增、移动、删除场景（含环检测） |
| 缓存测试 | 权限变更后 Redis 缓存是否正确失效、重新加载；系统配置修改后缓存是否同步刷新 |
| 操作日志测试 | 增删改操作是否被正确记录；日志列表分页与多条件筛选是否准确；日志清理定时任务是否正确删除过期数据 |
| 异步写入测试 | 操作日志的异步写入在高并发场景下是否会丢失数据，系统故障时日志队列的可靠性 |

### 7.2 前端测试（Vitest + React Testing Library）

| 测试范围 | 内容 |
|----------|------|
| 组件测试 | 关键共享组件（如树形选择器、权限树、按钮级权限组件、动态配置表单）的渲染与交互 |
| 页面测试 | 七大管理页面的列表渲染、分页切换、表单提交、筛选等交互 |
| 权限守卫测试 | 无权限用户能否看到隐藏菜单；按钮级权限是否正确控制显隐；非管理员能否看到/编辑敏感配置项 |
| 路由守卫测试 | Token 过期后自动跳转登录页；刷新后保持登录状态（refresh token 机制） |

### 7.3 E2E 测试（可选，后续补充）

- 完整的用户创建 → 分配角色 → 角色绑定权限 → 菜单生成 → 新用户登录验证权限的端到端流程

## 8. 已确认决策

以下问题已通过产品负责人确认，作为后续开发依据：

1. **用户-部门关系** → **单部门模式**。一个用户只能属于一个部门，前端列表页按部门字段筛选。
2. **删除策略** → **逻辑删除**（`is_deleted` 标记）。保留数据，禁止登录，用户名和邮箱不可复用（全局唯一约束）。
3. **超级管理员** → 系统首次启动时通过 seed 数据自动创建预设的 `admin` 账号，初始密码为 `admin`。该账号**跳过所有权限校验**，后端直接放行，前端返回全部菜单和按钮。
4. **菜单与权限的关系** → **独立维护，手动绑定**。菜单管理与权限管理各自维护独立的树形结构，通过菜单编辑页手动关联权限标识。
5. **权限粒度** → **三级权限**：菜单权限 + 按钮权限 + API 权限。后端每个接口均受权限标识管控，安全性优先。
6. **敏感配置存储** → **数据库加密存储**（AES 加密），API 始终返回脱敏格式（`******`），前端编辑时需重新输入完整值。
7. **操作日志写入方案** → **Redis 队列异步写入**。业务接口将日志信息推入 Redis 列表，后台独立 worker 批量消费写入数据库，最小化对业务接口的延迟影响。
